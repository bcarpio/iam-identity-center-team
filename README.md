# Temporary elevated access management (TEAM) for AWS IAM Identity Center

## This fork

This is a private-ingress fork of
[aws-samples/iam-identity-center-team](https://github.com/aws-samples/iam-identity-center-team).
It serves TEAM only inside a VPC: nothing TEAM runs has an inbound path from
the internet. The approval workflow, data model and IAM Identity Center
integration are unchanged, so upstream's user guides still describe how TEAM
is used.

It exists because a regulated customer's security review rejected upstream
TEAM: Amplify Hosting is always a public CloudFront distribution, the AppSync
API is a public endpoint, and their policy gives internally built privileged
tooling no inbound path from the internet. WAF allowlisting was not enough,
because the origin still answers on the internet. The full reasoning, and why
Cognito managed login stays public, is in
[ADR-001: Private ingress](docs/adr/ADR-001-private-ingress.md). The write-up
is [Making AWS TEAM Private: Everything but the Login Page](https://www.briancarpio.com/blog/private-aws-team).

### What changed

| Component | Upstream | This fork |
|---|---|---|
| SPA hosting | Amplify Hosting (public CloudFront) | nginx on ECS Fargate behind an internal ALB, private hosted zone |
| AppSync API | Public | `Visibility: PRIVATE`, via the `appsync-api` interface endpoint |
| Lambdas calling AppSync | No VPC | Private subnets (`teamRouter`, `teamStatus`, `teamgetEntitlement`, `teamGetPermissionSets`, `teamPublishOUs`, `teamgetLogs`) |
| Build/deploy | Amplify Hosting | CodeBuild (`amplify push`, frontend build, image push, UI service deploy) |
| Cognito managed login | Public | Still public (AWS offers no private path to it) |
| Session audit logs | CloudTrail Lake | CloudTrail Lake or CloudWatch Logs Insights on the org trail's log group |

Beyond private ingress:

- **CloudWatch Logs Insights audit backend.** CloudTrail Lake closed to new
  customers on 2026-05-31, so a fresh install cannot create an event data
  store. This fork carries upstream PR
  [#599](https://github.com/aws-samples/iam-identity-center-team/pull/599)
  (still open upstream), adapted to the private deploy path, and fixes its
  `logs:GetQueryResults` permission so query results actually return. Set
  `CLOUDTRAIL_AUDIT_LOGS=cwlogs://<log-group>` and `CWLOGS_ASSUME_ROLE_ARN`;
  see [cwlogs.md](docs/docs/deployment/configuration/cwlogs.md).
  `CLOUDTRAIL_AUDIT_LOGS=none` no longer creates an event data store.
- **Revoked requests** show "-" for the missing end time instead of a 1969
  or 1970 date.

### Why this will not be merged upstream

This fork is permanently divergent and its changes are not offered back:

- It removes Amplify Hosting, which is upstream's deployment model, and
  replaces it with infrastructure upstream would have to support.
- It requires a VPC, egress and corporate network reachability that the
  adopter provides. Upstream deploys into an account with no network
  prerequisites.
- Its deploy scripts (`deploy.sh`, `update.sh`, `destroy.sh`) are rewritten
  around CodeBuild, so upstream's deployment and update docs do not apply.

It does not track upstream PRs. Upstream fixes are picked up by hand when they
matter.

### Deploying this fork

Upstream's [deployment docs](https://aws-samples.github.io/iam-identity-center-team/docs/deployment/)
still explain the concepts (delegated administrator, the admin and auditor
groups, the IAM Identity Center SAML application), but follow these steps
rather than upstream's commands.

**Region.** Deploy in your IAM Identity Center region. TEAM's Lambdas call
`sso-admin` and `identitystore` in their own region. The reference deployment
was us-east-2.

**Network prerequisites (you provide):**
- A VPC with private subnets in two Availability Zones. `template.yml` reads
  them from SSM parameters `/network/vpc-id`, `/network/vpc-cidr` and
  `/network/private-subnet-ids` by default.
- Outbound egress to the AWS APIs TEAM calls: NAT, Transit Gateway to an
  egress VPC, or Direct Connect out through your datacenter. VPC endpoints can
  carry everything except Cognito, which narrows egress to one hostname,
  `cognito-idp.<region>.amazonaws.com`. **Do not create a `cognito-idp`
  endpoint with private DNS for this VPC**: it breaks request activation. The
  tested endpoint list is in ADR-001.
- The `appsync-api` interface VPC endpoint with private DNS enabled.
  Mandatory: a private AppSync API is reachable only through it.
- Network reachability from your users to the VPC (VPN, Direct Connect,
  Transit Gateway, or a tunnel).

**Steps** (all in `deployment/`):

1. Copy `parameters-template.sh` to `parameters.sh` (git-ignored) and fill it
   in, including `UI_DOMAIN` and the audit-log settings.
2. Run `./init.sh` with the management account profile to register the TEAM
   account as delegated administrator, as upstream does.
3. Certificate: set `UI_PUBLIC_ZONE_ID` if the public zone for `UI_DOMAIN` is
   in Route 53 in the TEAM account. Otherwise run `./request-cert.sh`, have
   the DNS owner add the printed validation CNAME, run
   `./request-cert.sh --wait`, and set `UI_CERTIFICATE_ARN`.
4. Run `./deploy.sh`. It ships `git archive HEAD`, so only committed code is
   deployed. `./update.sh` redeploys later changes.
5. Run `./integration.sh` for the start URL, ACS URL and SAML audience, and
   create the IAM Identity Center SAML application from them.
6. Save the application's metadata as `details.json` (from
   `details-template.json`) and run `./cognito.sh` to wire it into Cognito
   and point the callback at `https://<UI_DOMAIN>/`.

To test from outside the VPC, see the
[private access testing runbook](docs/private-access-testing.md).
`./destroy.sh` tears everything down.

## Upstream TEAM

The rest of this README is upstream's, describing TEAM itself.

TEAM is an open source solution that integrates with AWS IAM Identity Center and allows you to manage and monitor, time-bound elevated access to your multi-account AWS environment at scale.

The solution is a custom application that allows users to **request access to an AWS account** only when it is needed and only **for a specific period of time**. Once the time period has elapsed, elevated access is automatically removed.

Refer to the [blog post on the AWS Security Blog](https://aws.amazon.com/blogs/security/temporary-elevated-access-management-with-iam-identity-center/) for a background and an overview of the TEAM solution.
